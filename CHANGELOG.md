# Changelog

All notable changes to `opencode-mem0-selfhost` will be documented in this file.

## 0.1.0 — Initial self-host fork

### Changed (from upstream `@mem0/opencode-plugin` 0.2.0)

- **Replaced `mem0ai` SDK with a self-host REST client.** All memory operations
  are now plain `fetch` calls against `MEM0_HOST` (default `http://localhost:8888`).
  No `mem0ai` package dependency.
- **Auth is `X-API-Key: $MEM0_API_KEY`.** Self-host server-side auth, not the
  `m0-` Platform token scheme.
- **`MEM0_HOST` is the env var** (instead of earlier work's
  `MEM0_SELF_HOST_URL`). `MEM0_SELF_HOST_URL` is also accepted as a fallback
  for ergonomics.
- **Telemetry is opt-in, not opt-out.** `MEM0_TELEMETRY` defaults to `false`
  (the upstream plugin defaults to `true`). When opted in, the same
  PostHog-`plugin.*` schema and anonymized `sha256(apiKey)[:32]` identity are
  used.
- **No `mem0ai` project-categories auto-setup.** The self-host REST API does
  not expose `getProject`/`updateProject`; the call site is removed entirely
  (not stubbed — there is no functional equivalent).
- **No `dist/` in git.** The build artifact is generated by `bun run build`.
- **Removed the esbuild dep** that earlier work added. We use the same
  `bun build` + `tsc --emitDeclarationOnly` pipeline as upstream.

### Self-host limitations (inherited from the REST API)

- **`app_id` lives in metadata**, not as a top-level identity field. The plugin
  writes it to `metadata.app_id` and filters by it client-side on reads.
- **`delete_all_memories` is a list-then-delete loop.** The self-host admin
  bulk-delete endpoint ignores metadata filters, so the plugin fetches matching
  IDs and deletes them one at a time. Safe but slow for very large projects.
- **`delete_entities` and `list_entities` are no-ops.** The self-host REST API
  does not expose entity management; these tools return an `unsupported: true`
  response.
- **`get_event_status` is a compatibility stub.** Self-host writes are
  synchronous; the response from `add_memory` already contains the memory ID.
  Calling `get_event_status` returns `{status: "UNSUPPORTED", message: "..."}`
  so the existing skill files (which were written for the Platform) keep
  working without modification.
